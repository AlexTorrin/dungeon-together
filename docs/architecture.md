# Архитектура

## Поток данных

```
ввод (клавиши) ──► Command ──► shared.applyCommand(state, command) ──► { state, events }
                                                                           │
                         клиент проигрывает events как анимации ◄──────────┘
```

- **Клиент не меняет состояние сам.** Он только отправляет намерение (`Command`) в
  `GameSession` и рисует то, что пришло в событиях.
- `GameSession` (`client/src/game/GameSession.ts`) — интерфейс «игры» для сцены:
  `send(command)` ничего не возвращает, события и новое состояние приходят подписчикам
  (`subscribe((events, state) => …)`, возвращает отписку). Так устроена сетевая игра:
  ответ приходит позже, а события других игроков — вообще без нашего запроса.
- Реализаций две, сцена не знает, какая у неё:
  - `LocalGame` — одиночная игра: вызывает `shared` прямо в браузере и ведёт себя как маленький
    сервер — команду применяет сразу, а события доставляет **асинхронно** (`queueMicrotask`).
    Это нарочно: сцена, полагающаяся на синхронный ответ, сломалась бы уже в одиночной игре;
  - `NetworkGame` — сетевая: команда уходит на сервер, `{ events, state }` приходят оттуда
    (раздел «Сервер и сеть»).
- `shared` — чистые функции: одинаковый вход даёт одинаковый результат, без `Math.random`,
  `Date.now`, I/O. Это проверяет ESLint (`eslint.config.js`).

**Карта** хранится плоским массивом построчно: `tiles[y * width + x]`. Все изменения
возвращают новый объект — старое состояние никогда не мутируется.

**Акторы.** Все участники хода — игроки и монстры — лежат в одном `state.actors` по `id`;
различает их поле `kind` (`'player' | 'monster'`). У каждого `hp`, `maxHp`, `weapon`
(одно оружие или `null` — тогда кулаки) и `armor` (надетая броня или `null`). Стартовые
значения — в `config/actors.ts`, `config/weapons.ts` и `config/armor.ts`. id монстров и предметов порядковые (`monster-1`, `item-1`), поэтому
одинаковая комната всегда даёт одинаковое состояние. `state.items` — предметы на полу,
`state.status` — `'playing' | 'won' | 'lost'`.

**Случайность и id.** `Math.random()` в `shared` запрещён: сервер и клиенты должны
получать одинаковый результат. Вместо него в `GameState` хранится `rng` — 32-битное состояние
генератора (`rng.ts`). Каждый бросок — чистая функция `(rng) → [значение, новый rng]`, и новое
значение нужно записать обратно в состояние:

```ts
const [damage, rng] = nextInt(state.rng, 1, 4);
return { ...state, rng /* , ...урон */ };
```

Одинаковый seed + одинаковые команды → одинаковая игра (реплеи, отладка по seed, сверка с
сервером). Seed передаётся в `createGameState(room, playerIds, seed)`; в локальной игре его
выбирает клиент, в сетевой — сервер. Так же устроены id: `state.nextId` — счётчик,
`allocateId(nextId, 'monster')` → `['monster-7', 8]`. rot.js держит свой генератор глобально
(`ROT.RNG`), поэтому `generateLevel` засевает его прямо перед вызовом генератора, а в бою и ИИ
используется только `rng.ts`.

Состояние — простые объекты, массивы и числа (без `Map`, `Set`, классов), поэтому его можно
отправить по сети как JSON; это закреплено тестом.

**Комната** (`Room`) — карта, старт и расстановка `monsters` / `items` без id.

**ASCII-формат комнат:** `#` или пробел — стена, `.` — пол, `@` — точка старта (ровно одна).
Монстры: `S` — скелет, `K` — череп, `V` — вампир; оружие: `m` — ближнее, `r` — дальнее
(под ними всегда пол, в клетке — не больше одного). Им пользуются демо-карта, тесты,
редактор (кнопка «ASCII») и localStorage. Редактировать комнату — `setRoomTile`,
`setRoomEntity`, `setRoomSpawn`, `resizeRoom` (стена убирает того, кто стоял в клетке).

```
#######
#S.@.m#
#..K..#
#######
```

## Генерация уровня

`generateLevel(seed, difficulty): Room` (`map/generateLevel.ts`, параметры — `config/level.ts`)
отдаёт тот же `Room`, что делает редактор, поэтому дальше всё одинаково: `createGameState(room, …)`.

1. **Карта** — генератор `Digger` из [rot.js](https://ondras.github.io/rot.js/manual/):
   «копатель» прорубает комнату, от её стены — коридор и следующую комнату, и так, пока не
   прокопает нужную долю карты. Все клетки пола связаны (проверяется тестом). Стены толщиной
   в один тайл между коридорами — обычное дело, их рисует атлас стен (`docs/assets.md`).
2. **Старт** — центр первой комнаты. **Монстры, оружие и монеты** — на случайных свободных
   клетках остальных комнат (в стартовой никого нет), выбор — через наш `rng.ts` из того же seed.
3. **Сложность** (`DIFFICULTIES`: лёгкая, средняя, трудная) — сколько монстров и каких, сколько
   из них вооружено и чем, сколько монет на уровне (в среднем 2–3). Каждая монета с равным
   шансом лежит кучкой на полу или у случайного монстра (выпадет при смерти).
4. **Дверь-выход** — в верхней стене самой дальней от старта комнаты (снизу пол, сверху и по
   бокам стена); **ключ** — у случайного монстра. Места для двери нет — `door: null`, выход
   только через победу.

Детерминизм: одинаковый seed → одинаковый уровень. У rot.js свой глобальный генератор
(`ROT.RNG`): его засевают прямо перед `create()`, вызов синхронный — между ними никто другой
RNG не тронет, так что это безопасно и на сервере с несколькими играми. Версия `rot-js`
закреплена точно (`2.2.1`, без `^`): другая версия может построить по тому же seed другую карту.

`rot-js` импортируется из корня пакета: в `lib/` лежат ES-модули без `"type": "module"`, Node
их напрямую не загрузит, а корень отдаёт Vite ESM-сборку, а Node/Vitest — CommonJS-бандл.

## Недоверенные команды: `parseCommand`

`applyCommand` доверяет типам TypeScript, а в рантайме из сети придёт что угодно. Поэтому
на границе данные сначала проходят `parseCommand(raw: unknown): Command | null` — приём
«parse, don't validate»: `unknown` один раз превращается в строгий тип, дальше код работает
только с ним. Парсер собирает **новый** объект из известных полей (лишние поля и `__proto__`
отбрасываются), проверяет направление через `isDirection` и длину `playerId`.

Разделение ответственности:

- `parseCommand` проверяет только **форму** команды;
- `applyCommand` / `submitPlan` — **правила** (есть ли такой игрок, ходит ли он ещё в этом ходу, достают ли удары);
- сервер (шаг 6) — **кто прислал**: `playerId` подставляет из сессии, а не берёт из сообщения.

Без парсера одна команда с неизвестным направлением сохранялась в плане хода и роняла
разрешение хода у всех — тест в `parseCommand.test.ts` это закрепляет.

## Суть игры и очерёдность ходов

Игра на угадывание: все выбирают действия втайне от монстров, потом ход разрешается разом.
Удар бьёт **клетку**, а не актора, и считается по позициям **после** шагов своей фазы: угадал,
куда отойдёт противник, — попал; отошёл из-под удара — увернулся. Бить можно и пустое место.

**Ход — 2 очка действия и две фазы** (`ACTION_POINTS`, `config/turn.ts`). Каждый планирует
до двух действий: фаза 1 разрешается у всех разом, потом фаза 2. Шаг, удар и ожидание стоят
по 1 ОД; действие дороже (меч, шаг 6 roadmap) займёт несколько фаз и сработает в последней.
Угадывать приходится двухходовку: «шаг + удар», «удар + отход», «ждать + удар» по тому, кто
придёт.

1. Игрок шлёт `{ type: 'submitPlan', playerId, plan }`, `plan` — массив из 1–2 действий:
   шаг `move` в одну из 8 сторон, удар `attack` по клетке `target` или `wait`. План кладётся в
   `state.pendingPlans`, клиенты получают `planSubmitted`. Отказ — событие `planRejected` с
   причиной (`gameOver`, `alreadySubmitted`, `invalidPlan`), состояние не меняется: план после
   конца игры, повторный план в том же ходу, план дороже ОД или с ударом, который не достаёт с
   **ожидаемой** позиции — той, куда игрок придёт после своих шагов, если они удадутся
   (`rules/plan.ts`: `planPhases`, `expectedPositions`, `isPlanValid`). Неизвестный id или id
   монстра игнорируются молча — сообщать некому. Поиск по id — через `Object.hasOwn`.

   Раньше отказ был молчаливым, и клиент, отправивший неверный план, ждал ответа вечно
   («зависший» ход). Теперь клиент проверяет план той же `isPlanValid` до отправки, а на
   `planRejected` снимает «отправлено».
   `{ type: 'cancelPlan', playerId }` отзывает отправленный план, пока ход не разрешён
   (`planCancelled`).

2. Когда план есть у **всех игроков**, `resolveTurn`:
   1. **Планы.** Игроки — что выбрали (короткий план дополняется ожиданием). Монстры —
      `chooseMonsterPlan` по состоянию на начало хода: выбор игроков ему не виден, бот тоже
      угадывает; второе действие выбирается так, будто первое удалось.
   2. **Фазы по очереди** (`resolvePhase`), в каждой:
      1. **шаги** — одновременно, с конфликтами (таблица ниже), события `moved` / `bumped`;
      2. **подбор** — кто шагнул на клетку с предметами, кладёт их в рюкзак, пока есть место
         (`itemPickedUp`); взять в руки (надеть) / выбросить — `equip` / `drop` (`itemEquipped`,
         `itemDropped`);
      3. **удары** (`attacked`) по клеткам после шагов этой фазы, урон (`damaged`) разом —
         убитый в этой фазе тоже успевает ударить. Удар, который с фактической позиции уже
         не достаёт (шаг перед ним не удался, клетку не видно), срывается и считается
         ожиданием (`waited`). Надетая броня срезает урон каждого удара (`damageThrough`).
         Дружественный огонь есть;
      4. **смерти** (`died`) — актор удаляется, всё, что нёс (руки, броня, рюкзак), падает на пол.
         Убитый в фазе 1 во второй не действует.

      После фазы — событие `phaseResolved` (клиент проигрывает фазы по очереди).

   3. **Конец уровня** (`gameOver`): убит последний монстр — `won`, все живые уносят добычу; на
      уровне не осталось игроков — `won`, если кто-то вышел через дверь, иначе `lost`.
      Вынесенное (монеты, руки, броня, рюкзак) — в `state.escaped` для хаба.
   4. **Память команды** (`explored`) пополняется.
3. Монстры ход не задерживают и живут по тем же правилам, что игроки.

## Инвентарь

У актора **руки** (`weapon`: одно оружие или ничего — кулаки), **броня** (`armor`: надетая
броня или ничего) и **рюкзак** (`backpack`, до
`BACKPACK_SIZE` = 4 предметов, `config/inventory.ts`). Правила одни для игроков и монстров.

- **Подбор** — шагнул на клетку с предметами: всё, что влезает, уходит в рюкзак, в руках
  ничего не меняется; не влезло — лежит дальше. Стоя на месте, не подбирают.
- **`equip`** (1 ОД) — взять оружие из рюкзака в руки или надеть броню; то, что было в руках
  (надето), встаёт в рюкзак на его место. Баночку — нельзя, её пьют (`drink`).
- **`drop`** (1 ОД) — выбросить предмет из рук, с себя или из рюкзака на свою клетку: так добычу отдают
  союзнику (выбросил, отошёл, тот наступил).
- **Монеты и ключи** места в рюкзаке не занимают — это счётчики `coins` и `keys`. Наступил на
  кучку монет или ключ — подобрал. `dropCoins` / `dropKey` (1 ОД) — выбросить кучкой на свою
  клетку (новая вещь на полу с новым id из `nextId`).
- **Смерть** — на пол падает всё: руки, броня, рюкзак, монеты (одной кучкой), ключи.

Вещь на полу (`GroundItem`) — одна из: оружие, броня, баночка, кучка монет, ключ (`Loot`).

## Дверь-выход

`state.door` — `{ pos, open }` или `null`. Закрытая дверь в карте — стена. **`openDoor`**
(1 ОД, `canOpenDoor`): стоять вплотную (в т.ч. по диагонали) и иметь ключ; ключ тратится,
дверь становится проходом — клетка в карте превращается в пол (`doorOpened`). **Игрок,
шагнувший в открытую дверь, покидает уровень** со всем, что несёт (`exited`, `state.escaped`).
Монстры через дверь не уходят. Проверке плана нужна дверь, поэтому `simulatePlan` и
`isPlanValid` принимают «мир» (`World` — карта и дверь), а не только карту.

**План «в уме»** (`rules/plan.ts`, `simulatePlan`): цена удара зависит от оружия в руках, а оно
меняется по ходу плана (`equip`), поэтому план проигрывается заранее — где актор будет и что у
него будет в руках и в рюкзаке к каждой фазе (`before`), в какой фазе срабатывает каждое
действие (`phaseOf`), сколько ОД занято (`used`). На этом стоят проверка плана (`isPlanValid`),
разбивка по фазам в `resolveTurn`, номера фаз и выбор действий на клиенте.

## Поле зрения и туман войны

**Поле зрения (FOV)** — какие клетки видно из точки (`map/fov.ts`). Алгоритм — recursive
shadowcasting из rot.js: из глаза по восьми секторам расходятся «лучи», стена отбрасывает тень на
клетки за ней. Стены в поле зрения тоже видны. Радиус обзора — `VIEW_RADIUS` (`config/vision.ts`),
круглый. Акторы обзор не закрывают.

- **«Видеть» значит одно и то же везде:** туман войны, удар по клетке (`canAttack`) и ИИ монстров
  (замечает игроков и предметы, только если видит их) пользуются одним полем зрения.
- **Видимость общая на команду** (`teamVision`): видно то, что видит хоть кто-то из игроков.
  Она не хранится в состоянии — выводится из позиций.
- **Память** — `state.explored`: клетки, которые команда уже видела (индекс `y * width + x`).
  Пополняется в `createGameState` и в конце каждого хода (`resolveTurn`, фаза 7).

На клиенте (`render/FogLayer.ts`) у клетки три состояния: не исследована — закрыта фоном;
исследована, но не видна — затемнена (стены помним, монстров и предметы не показываем); видна —
без тумана. Путь по клику мыши прокладывается по «известной карте», где неисследованное —
стена, иначе он выдал бы скрытую планировку. Сейчас клиент получает всё состояние целиком,
поэтому туман — честность отображения, а не защита: на шаге 6 сервер будет отправлять каждому
только то, что видит команда.

## Бой и оружие

`rules/combat.ts`, константы — `config/weapons.ts`.

| Оружие           | Урон | Дальность                              | Удар   |
| ---------------- | ---- | -------------------------------------- | ------ |
| кулаки           | 1    | 1 — соседние 8 клеток                  | 1 ОД   |
| нож (`knife`)    | 3    | 1                                      | 1 ОД   |
| лук (`bow`)      | 2    | 4 — любая клетка в квадрате 9×9 вокруг | 1 ОД   |
| меч (`sword`)    | 6    | 1                                      | 2 ОД ⚔ |
| палочка (`wand`) | 3    | 6                                      | 1 ОД   |

⚔ Удар дороже 1 ОД — **замах**: занимает несколько фаз и срабатывает в последней, до него
актор стоит на месте. Удар мечом — весь ход, бьёт во второй фазе: от него можно успеть уйти.
Цена удара зависит от оружия в руках **в момент удара** (`actionCost(action, weapon)`).

Дальность — **расстояние Чебышёва** (`max(|dx|, |dy|)`): диагональный шаг считается за один.
Ударить можно клетку пола (не свою), если атакующий её **видит** — то же поле зрения, что и для
тумана войны (`map/fov.ts`, ниже). Акторы обзор не закрывают. Поле зрения rot.js круглое, а
дальность оружия — квадрат, поэтому видимость для удара считается с радиусом ⌈дальность·√2⌉.
`attackableCells` отдаёт все доступные клетки — для подсветки на клиенте.

**Броня** (`config/armor.ts`) уменьшает урон каждого удара на свою защиту, но не ниже
`MIN_DAMAGE` = 1 (неуязвимых нет): кожанка (`leather`) −1, кольчуга (`mail`) −2. Считается для
каждого удара отдельно — два удара ножом (3) по кольчуге — это 1 + 1, а не 6 − 2.

**ИИ монстра** (`chooseMonsterAction`), по порядку:

1. Безоружный, а в рюкзаке есть оружие → берёт лучшее в руки; без брони, а в рюкзаке есть
   броня → надевает лучшую.
2. Игрок в досягаемости и на удар хватает ОД → бьёт. С шансом `AI_AIM_AT_CURRENT_CHANCE` — туда,
   где игрок стоит, иначе в случайную соседнюю с ним клетку, куда тот может шагнуть («угадывает»
   отход). Не хватает ОД (замах мечом после шага) — ждёт.
3. Безоружный с пустым рюкзаком и предмет не дальше `ITEM_SEARCH_RADIUS` → идёт за предметом.
4. Игрок не дальше `AGGRO_RADIUS` по пути → идёт к нему.
5. Иначе ждёт.

План монстра (`chooseMonsterPlan`) — действия, пока хватает ОД; каждое следующее выбирается так,
будто предыдущее удалось (шаг — уже на новой клетке, `equip` — оружие уже в руках).

Случайность — только через `state.rng`, поэтому одинаковый seed даёт одинаковые решения.

**Поиск пути** (`map/pathfinding.ts`): `findPath` — поиск в ширину (BFS) по 8 направлениям,
акторы путь не загораживают (все ходят одновременно). `canStep` — можно ли шагнуть: в клетке
пол, а по диагонали ещё и не срезается угол стены (обе прямые соседние клетки — пол).

**Конфликты** (`resolveMoves`) решаются без случайности и не зависят от порядка выбора:

| Ситуация                                          | Результат                   | `reason` в `bumped` |
| ------------------------------------------------- | --------------------------- | ------------------- |
| `wait` или `attack`                               | стоит, занимает свою клетку | —                   |
| Шаг в стену или по диагонали через угол стены     | стоит                       | `wall`              |
| Двое в одну клетку                                | оба стоят                   | `contested`         |
| Двое меняются местами (и по диагонали)            | оба стоят                   | `swap`              |
| Пути пересекаются по диагонали (крест-накрест)    | оба проходят                | —                   |
| В клетку того, кто стоит                          | стоит                       | `occupied`          |
| В клетку, которую сосед в этот же ход освобождает | проходит (цепочки работают) | —                   |

Алгоритм итеративный: провал одного может вызвать провал того, кто шёл за ним,
поэтому проверки повторяются, пока ничего не меняется.

Таймера хода нет: отошедший игрок блокирует всех. Если понадобится — он будет на сервере.

## client: сцены

`BootScene` → `MenuScene` ⇄ `GameScene` ⇄ `RoomEditorScene`, `MenuScene` ⇄ `HubScene`,
`MenuScene` ⇄ `LobbyScene` → `GameScene`. Ключи сцен и типы данных,
которые они передают друг другу, — в `scenes/sceneKeys.ts`.

| Сцена             | Заметки                                                                                                                                                                                                                                                   |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BootScene`       | грузит тайлсет, спрайт-лист и покадровые анимации, регистрирует анимации                                                                                                                                                                                  |
| `MenuScene`       | фон — демо-карта; забег выбранной сложности (`startRun`), лагерь, тренировка (демо, редактор, свои комнаты)                                                                                                                                               |
| `GameScene`       | один игрок за компьютером (hot-seat убран — дальше сеть). Ввод «черновик → подтверждение» (ниже). Сцена — дирижёр: рисуют слои `render/ActorLayer`, `ItemLayer`, `IntentLayer`, всплывашка — `ui/ActionPopup`. Подписка на сессию снимается на `shutdown` |
| `RoomEditorScene` | всё состояние — один `EditorDraft`; каждое изменение пересоздаёт карту целиком (комнаты маленькие). Инструменты 1–8: стена, пол (заодно стирает монстров и предметы), старт, три вида монстров, два вида оружия                                           |

Особенности, о которые уже спотыкались:

- **Две камеры.** Главная приближена (`ZOOM = 3`) и следует за героем, UI рисует отдельная
  камера в масштабе 1:1 (`ui/UiOverlay.ts`). Каждый новый объект нужно зарегистрировать:
  `ui.world(obj)` — только мир, `ui.add(obj)` — только UI. Иначе его нарисуют обе камеры.
- **Не использовать `Phaser.GameObjects.Layer` со спрайтами.** При остановке сцены слой
  уничтожается раньше вложенных спрайтов, и Phaser падает (`reading 'indexOf'`).
- **Клик по кнопке всплывашки не должен считаться кликом по карте.** Обработчик
  `pointerdown` сцены получает список объектов под курсором и, если он не пуст, клик пропускает.
- **Цифры урона всплывают с задержкой** на длину анимации шага: удар считается по позициям после
  шагов, и цифра должна появиться там, где жертва оказалась, а не там, откуда ушла.
- `main.ts` в dev-режиме кладёт игру в `window.__game` (для отладки и скила `run-game`).

## client: ход игрока — черновик и подтверждение

План хода собирается в два этапа (паттерн «черновик → подтверждение»), всё состояние — в `GameScene`:

| Поле    | Что это                                                                                                    |
| ------- | ---------------------------------------------------------------------------------------------------------- |
| `draft` | выбранные действия по фазам (0–2): стрелки полупрозрачные, выбор можно менять сколько угодно               |
| `sent`  | подтверждённый план, отправленный в сессию: стрелки сплошные, над героем ✓; сбрасывается на `turnResolved` |
| `goal`  | клетка, к которой идём мышью; после каждого хода следующие шаги к ней сами становятся `draft`              |

Первое выбранное действие — фаза 1, второе — фаза 2, следующие заменяют последнее; Backspace
убирает последнее. Каждое действие выбирается **от клетки, куда герой придёт** после выбранных
раньше шагов (`chooser()` → `expectedPositions`): от неё считаются шаг, удар рядом, досягаемость,
прицел и путь мыши. Enter отправляет план (недостающая фаза — ожидание). В `shared` уходит только
подтверждённое — черновик правила не видят. Выбор:

- **WASD / стрелки** — шаг; две клавиши сразу — по диагонали (`input/keyDirection.ts`:
  направление считается по всем зажатым клавишам в момент нажатия, противоположные гасятся).
- **Shift + направление** — удар по соседней клетке. Пока Shift зажат, подсвечены все клетки,
  которые можно ударить (`attackableCells`).
- **Пробел** — ждать. **Enter** — подтвердить. **Backspace** — убрать последнее действие.
  **ПКМ / Esc** — очистить план (черновик, прицел, всплывашку, цель мыши); если план уже
  отправлен, а ход не разрешён — отозвать его (`cancelPlan`). Esc без плана — выход.
- **Клик по клетке** — всплывашка «Ударить / Идти (N шаг.) / Ждать / Отмена». Наведение на пункт
  показывает намерение заранее, пункт добавляет действие в план; если план заполнен — это и есть
  подтверждение. План и фаза запоминаются при открытии всплывашки: предпросмотр пишет в черновик
  от этой базы, иначе он сдвигал бы фазу и удар проверялся бы не с той клетки. «Отмена»
  возвращает план, каким он был до клика. По клетке, где кто-то стоит, первым идёт «Ударить». «Идти» к дальней клетке
  заполняет оставшиеся фазы шагами по пути (`findPath`) и запоминает `goal`.
- **Двойной клик** (второй клик по той же клетке быстрее `DOUBLE_CLICK_MS`; в Phaser такого
  события нет) — план на весь ход без всплывашки и сразу подтверждение: пол — шаги по пути
  (+ `goal`, если дальше), видимый монстр — шаг к нему и удар по его клетке, если после шага
  достаёт (`approachAndAttack`); уже рядом — два удара; далеко — два шага навстречу; своя
  клетка — ждать.

**Проигрывание по фазам.** События хода приходят одним пакетом; сцена режет их по
`phaseResolved` и проигрывает фазу за фазой: следующая — когда закончились анимации предыдущей
(колбэк `ActorLayer`). Спрайты к новому состоянию сначала только готовятся (`ActorLayer.prepare`:
новые спрайты, туман), а выравниваются по клеткам и убираются у погибших (`sync`) — когда
проиграны все фазы. Погибший гаснет сразу в своей фазе.

**Лог хода** — нижняя строка HUD, по фазам: «ф1: вы — мимо · ф2: вы попали: скелет −3». Кто кого
ударил и на сколько, промахи, кто погиб, кто что подобрал и что осталось на полу (про героя и тех,
кого видно). **Промах** — удар фазы, после которого в той же фазе нет ни одного `damaged` от этого
атакующего: над клеткой всплывает серое «мимо». Два удара в одну клетку — два отдельных удара в
двух фазах: каждый всплывает своей цифрой (−3 и −3), итог видно по полоске HP.

**Намерения на карте** (`render/IntentLayer.ts`): номер фазы у каждого действия, стрелка шага, пунктир оставшегося пути до
`goal`, красное перекрестие на клетке удара, кружок у ожидающего. Подтверждённые действия других
игроков (`state.pendingPlans`, обе фазы) рисуются всем; намерения монстров — никогда, их надо угадывать.
Черновики других игроков пока не видны: для этого нужна отдельная команда по сети (шаг 6).

## client: акторы на экране

`GameScene` рисует **всех** из `state.actors`, а не только локальных игроков: монстров и игроков
с других компьютеров тоже. Внешний вид решает клиент (`render/actorLooks.ts`): у локальных
игроков свой облик, у остальных игроков — общий «чужой», у монстров — по виду (`species`).

Спрайты поддерживаются **сверкой** (reconciliation), как React сверяет DOM с данными: после
каждого пакета событий `ActorLayer.sync(state)` создаёт спрайты новым акторам и убирает спрайты
пропавших (умер, вышел). Двигают спрайты только события (`moved` / `bumped` → tween).
Пока идут анимации хода, сверка только создаёт: уничтожить или передвинуть спрайт посреди
tween нельзя — его `onComplete` не сработает, счётчик анимаций не обнулится, и ввод заблокируется
навсегда. Остальное делается после последней анимации; заодно спрайты встают ровно в клетки
из состояния — страховка от рассинхрона по сети. Под каждым актором — полоска HP, над
игроками — ✓ «готов», а в сетевой игре ещё и имя из лобби (`PlayerLabels`; своё — жёлтым).
Подпись прячется, гаснет и удаляется вместе со спрайтом. Предметы на полу (`ItemLayer`) сверяются так же, но после анимаций —
иначе подобранный предмет исчезал бы раньше, чем до него дойдут.

## client: рендер карты

- `render/tilesetIndex.ts` — кадры пола в тайлсете пака (подробно — `docs/assets.md`).
- `render/autotile.ts` — **автотайлинг**: в `shared` клетка — просто `wall` или `floor`,
  а какой спрайт рисовать, клиент решает по соседям. Стены — **по битовой маске** (bitmask
  autotiling): у клетки смотрим 8 соседей, бит = «там пол», маска 0–255 — номер кадра в атласе
  `assets/custom/walls.png` (×4 варианта кладки). Атлас собран заранее из кусков тайлсета
  (`tools/sprites/walls.mjs`), поэтому любые сочетания — столбы, перегородки в один тайл,
  Т-стыки — выглядят как часть пака; торцы и столбы — сплошные блоки. Пол прямо под стеной получает тайл с тенью. Стена без
  соседнего пола не рисуется — там фон `#25131a`. Вариант тайла выбирается хешем координат,
  а не случайно, чтобы картинка была стабильной.
- `render/mapView.ts` — `MapView`: тайлмап + декоративные факелы на стенах с кирпичной гранью.
  Слой тайлмапа берёт тайлы из двух тайлсетов (пак и атлас стен): у каждого свой диапазон
  номеров (gid), атлас стен начинается с 1000.

## Лагерь и профиль (мета-прогрессия)

Рогалик проходится забегами: внутри забега всё рискованно, а между забегами копится то, что
переживает смерть. Это **профиль** (`shared/src/hub/profile.ts`): `{ coins, hands, armor,
backpack, chest }`, предметы — просто `ItemType` (id им выдаются только в забеге). Профили,
записанные до брони, без поля `armor` — `parseProfile` читает их как «без брони». Действия лагеря —
`HubAction` (`buy` / `sell` / `move`, `shared/src/hub/actions.ts`), применяет их чистая функция
`applyHubAction(profile, action) → Profile | null` (null — нельзя); цены — в `config/shop.ts`.

**Профиль живёт на сервере**, клиент знает только свой **токен** — случайный UUID в localStorage
(`client/src/storage/playerToken.ts`, ключ `dt.token.v1`). Логина нет: потерял токен (очистил
данные сайта, другой браузер) — потерял профиль.

- `server/src/ProfileStore.ts` — профили в памяти и в JSON-файле `packages/server/data/profiles.json`
  (в git не попадает; путь меняет `DT_PROFILES_FILE`). Ключ — SHA-256 токена, а не сам токен.
  Файл пишется целиком, атомарно (временный файл + rename), записи по очереди. Битый файл —
  сервер не стартует, а не обнуляет профили молча.
- `server/src/routes.ts` — HTTP на том же порту, токен в `Authorization: Bearer …`:
  `GET /profile` и `POST /profile/action` (тело — `HubAction`; 400 — мусор, 409 — нельзя,
  401 — нет токена). Клиент — `client/src/net/profileApi.ts`, сцена `HubScene` (какие кнопки
  показать, решает тем же `applyHubAction`, но меняет профиль только ответ сервера).

Жизненный цикл забега — целиком на сервере (`DungeonRoom`), клиенту не верим:

1. Вход в комнату — с токеном (`JoinOptions.token`); без токена или второй раз с тем же — отказ.
2. Старт: `startRun(profile)` → `{ profile, loadout }` — руки, броня и рюкзак убираются из профиля
   **сразу**. Бросил забег, отключился, погиб — снаряжения больше нет.
   `createGameState(room, ids, seed, loadouts)` выдаёт предметам id из `nextId`.
3. После каждой команды: кто попал в `state.escaped` (вышел дверью, или все живые при победе) —
   `finishRun(profile, carried)`, ровно один раз. Возвращённое **добавляется**: в руки (броня —
   на героя), если пусто, иначе в рюкзак, иначе в сундук — профиль мог измениться, пока шёл забег.

Одиночный забег из меню — тоже комната на сервере, просто на одного (`LobbyScene` с `solo`
создаёт её и сразу начинает). В браузере (`LocalGame`) считаются только тренировки: демо, свои
комнаты, тест из редактора — без снаряжения и без записи в профиль. Своя комната в сетевой игре —
тоже тренировка, хоть и на сервере: `DungeonRoom` не зовёт `startRun`/`finishRun`, а клиент
получает `practice: true` (нет «Добыча — в лагере» и подтверждения выхода).

## Хранение комнат

`storage/roomStorage.ts`, ключ localStorage `dt.rooms.v1`: массив `{ id, name, ascii }`.
При чтении битые записи пропускаются. Комнаты живут только в конкретном браузере,
для переноса — кнопка «ASCII» в редакторе.

## Сервер и сеть

```
клиент A ─┐  'command' {type, plan}           ┌─► 'events' {events, state} ─► клиент A
клиент B ─┴─► DungeonRoom: parseCommand ──► applyCommand ──────────────────┴─► клиент B
               (playerId — по соединению)
```

- `packages/server` — Colyseus (`@colyseus/core` + `@colyseus/ws-transport`), порт 2567.
  `src/createServer.ts` — сервер с одной комнатой `dungeon`, `src/DungeonRoom.ts` — партия на
  1–4 игроков. Запуск без сборки: `tsx` (`pnpm dev:server`, в `pnpm dev` — вместе с клиентом).
- **Протокол** — `shared/src/net/protocol.ts`: типы сообщений (`ClientMessages`,
  `ServerMessages`) и разбор недоверенных опций (`parseCreateOptions`, `parseJoinOptions`,
  `parseRoomCode`). `parseCreateOptions` отдаёт `LevelChoice`: подземелье сложности или своя
  комната — её ASCII из localStorage хоста (`custom: { name, ascii }`) сервер разбирает тем же
  `parseRoom`, не больше `MAX_CUSTOM_ROOM_SIZE` (64) по стороне; не разобралась — комната не
  создаётся. В лобби уходит только `level` (сложность или название), карту видно уже в игре. Сетевого кода в shared нет — только типы и проверки.
- **Без Schema.** Colyseus умеет синхронизировать состояние сам, но для этого его надо описать
  своими классами (`@colyseus/schema`). Наше состояние — простые объекты из shared, и ход —
  редкое событие, поэтому сервер просто шлёт его целиком (msgpack) после каждой команды.
  Плата — трафик (карта целиком в каждом сообщении) и то, что клиент видит всё состояние,
  включая монстров в тумане: для кооператива это приемлемо.
- **Сервер авторитетен.** Клиент шлёт `{ type, plan }` без `playerId`; сервер добавляет
  `playerId` по соединению и пропускает через `parseCommand` — походить за другого нельзя.
  Команду `leave` клиент послать не может (`parseCommand` её не принимает) — её применяет сервер
  в `onLeave`.
- **Жизненный цикл комнаты:** создание (хост выбирает сложность или свою комнату; код — 4 буквы, это и есть
  `roomId`) → лобби (сообщение `lobby` при каждом изменении состава, у каждого своё `you`) →
  хост шлёт `start` → сервер генерирует уровень (seed — `crypto.randomInt`), создаёт состояние
  со снаряжением игроков и закрывает комнату (`lock`) → `started` → команды и `events`.
- **Ушёл игрок** (Esc, или не вернулся после обрыва связи) — правило `leave` в shared: игрок покидает
  уровень, всё, что нёс, падает на пол; если остальные уже ждут — ход разрешается. Иначе
  ушедший блокировал бы ход всем. Но сначала сервер ждёт его возвращения (ниже).
- **Обрыв связи и возврат.** Colyseus различает уход по согласию (`room.leave()`, код 4000 —
  сразу `onLeave`) и обрыв (закрыл вкладку, пропала сеть — `onDrop`). В `onDrop` сервер шлёт всем
  `playerStatus {online: false}` и держит место `RECONNECT_SECONDS` (30 с,
  `allowReconnection`); всё это время ход ждёт и его. Вернулся — `onReconnect` (тот же
  `sessionId`, место то же), `playerStatus {online: true}`; не успел — `onLeave` и правило `leave`.
  - Сеть мигнула: SDK переподключается сам (до 15 попыток, только если в комнате больше 5 с),
    отправленное за это время копит и досылает. Пришедшее за время обрыва потеряно, поэтому
    клиент после `onReconnect` шлёт `resync`, а сервер отвечает `lobby` и `sync {state, title}` —
    состояние целиком. `GameScene.resync` не проигрывает пропущенное, а встаёт в новое состояние
    (карта, дверь, туман, акторы, предметы, кто уже отправил план).
  - Перезагрузка страницы: `net/resume.ts` держит в sessionStorage код комнаты и
    `reconnectionToken` (переживает перезагрузку, но не закрытие вкладки). В меню появляется
    «↩ Вернуться в игру», `client.reconnect(token)` → `Lobby` сразу шлёт `resync` и по ответу
    понимает, где мы — в лобби или уже в игре (`sync`). Ушли по своей воле или игра кончилась —
    запись стирается.
- **Клиент:** `net/connection.ts` (адрес сервера: `VITE_SERVER_URL` или тот же хост, порт 2567;
  путь вида `/server` — сервер за тем же доменом через прокси, так собирает `deploy/ubuntu.sh`),
  `net/Lobby.ts` (подключение до старта — живёт дольше сцены, которая перерисовывается через
  `restart`), `scenes/LobbyScene.ts`, `game/NetworkGame.ts`. NetworkGame создаётся прямо в момент
  `started`, чтобы не пропустить ни одного `events`.
- **Профиль** — на сервере, по токену из `JoinOptions` (раздел «Лагерь и профиль»).
- Тесты поднимают настоящий сервер и клиентов SDK: `DungeonRoom.test.ts` — лобби, токены, старт,
  подмена `playerId`, разрешение хода, уход игрока, закрытая комната; `runProfile.test.ts` —
  снаряжение из профиля и добыча обратно (своя маленькая комната через
  `createServer(store, { level })`; там же своя комната — профиль не меняется); `routes.test.ts` — маршруты лагеря; `ProfileStore.test.ts`.

## Запуск в песочнице агента

Скил `.claude/skills/run-game` поднимает dev server и делает скриншоты через headless
Chromium (с кликами и нажатиями клавиш). Если папка смонтирована с Windows, pnpm не может
создать в ней симлинки, поэтому скил ставит зависимости в зеркало `/tmp/dt-run/ws`.
Подробности — в `SKILL.md`. На обычной машине достаточно `pnpm install && pnpm dev`.
