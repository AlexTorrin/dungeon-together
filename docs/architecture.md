# Архитектура

## Поток данных

```
ввод (клавиши) ──► Command ──► shared.applyCommand(state, command) ──► { state, events }
                                                                           │
                         клиент проигрывает events как анимации ◄──────────┘
```

- **Клиент не меняет состояние сам.** Он только отправляет намерение (`Command`) в
  `GameSession` и рисует то, что пришло в событиях.
- `GameSession` (`client/src/game/GameSession.ts`) — интерфейс «игры» для сцены.
  Сейчас есть одна реализация, `LocalGame`: она вызывает `shared` прямо в браузере.
  На шаге 6 появится сетевая реализация с тем же интерфейсом: команды уйдут на сервер,
  события придут оттуда. Сцены переписывать не придётся.
- `shared` — чистые функции: одинаковый вход даёт одинаковый результат, без `Math.random`,
  `Date.now`, I/O. Это проверяет ESLint (`eslint.config.js`).

## shared: модель

`packages/shared/src/` — всё экспортируется через `index.ts`.

| Файл                                                                     | Что внутри                                                                                               |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| `types.ts`                                                               | `Position`, `Tile`, `GameMap`, `Room`, `Actor` (игрок или монстр), `Item`, `Action`, `GameState`         |
| `commands.ts`                                                            | `Command` (что шлёт клиент) и `GameEvent` (что происходит) — discriminated unions по `type`              |
| `direction.ts`                                                           | `Direction`, `step(pos, dir)`, `isDirection` (пригодится для валидации на сервере)                       |
| `parseCommand.ts`                                                        | `parseCommand` / `parseAction`: `unknown` из сети → `Command` / `Action` или `null`                      |
| `rng.ts`                                                                 | детерминированный генератор случайных чисел (mulberry32): `seedRng`, `nextFloat`, `nextInt`, `chance`    |
| `map/gameMap.ts`                                                         | `getTile` (за краем — стена), `isWalkable`, неизменяемые `setTile` и `resizeMap`                         |
| `map/parseAsciiMap.ts`, `map/room.ts`                                    | ASCII ⇄ карта/комната, `createEmptyRoom`, `setRoomSpawn`, `resizeRoom`                                   |
| `map/demoMap.ts`                                                         | `DEMO_ROOM` — временная демо-карта до появления генератора                                               |
| `state/createGameState.ts`                                               | начальное состояние: монстры и предметы из комнаты, игроки — на старт и ближайшие свободные клетки (BFS) |
| `state/ids.ts`                                                           | `allocateId` — id новых сущностей из счётчика `state.nextId`                                             |
| `rules/applyCommand.ts`                                                  | единая точка входа логики                                                                                |
| `rules/submitAction.ts`, `rules/resolveTurn.ts`, `rules/resolveMoves.ts` | очерёдность ходов (ниже)                                                                                 |

**Карта** хранится плоским массивом построчно: `tiles[y * width + x]`. Все изменения
возвращают новый объект — старое состояние никогда не мутируется.

**Акторы.** Все участники хода — игроки и монстры — лежат в одном `state.actors` по `id`;
различает их поле `kind` (`'player' | 'monster'`). У каждого `hp`, `maxHp` и `weapon`
(одно оружие или `null` — тогда кулаки). Стартовые значения — в `config/actors.ts` и
`config/weapons.ts`. id монстров и предметов порядковые (`monster-1`, `item-1`), поэтому
одинаковая комната всегда даёт одинаковое состояние. `state.items` — предметы на полу,
`state.status` — `'playing' | 'won' | 'lost'`.

**Случайность и id.** `Math.random()` в `shared` запрещён: сервер и клиенты должны
получать одинаковый результат. Вместо него в `GameState` хранится `rng` — 32-битное состояние
генератора (`rng.ts`). Каждый бросок — чистая функция `(rng) → [значение, новый rng]`, и новое
значение нужно записать обратно в состояние:

```ts
const [damage, rng] = nextInt(state.rng, 1, 4);
return { ...state, rng /* , ...урон */ };
```

Одинаковый seed + одинаковые команды → одинаковая игра (реплеи, отладка по seed, сверка с
сервером). Seed передаётся в `createGameState(room, playerIds, seed)`; в локальной игре его
выбирает клиент, в сетевой — сервер. Так же устроены id: `state.nextId` — счётчик,
`allocateId(nextId, 'monster')` → `['monster-7', 8]`. rot.js держит свой генератор глобально
(`ROT.RNG`), поэтому при генерации уровня его нужно засевать из `state.rng` прямо перед вызовом,
а в бою и ИИ использовать только `rng.ts`.

Состояние — простые объекты, массивы и числа (без `Map`, `Set`, классов), поэтому его можно
отправить по сети как JSON; это закреплено тестом.

**Комната** (`Room`) — карта, старт и расстановка `monsters` / `items` без id.

**ASCII-формат комнат:** `#` или пробел — стена, `.` — пол, `@` — точка старта (ровно одна).
Им пользуются демо-карта, тесты, редактор (кнопка «ASCII») и localStorage.
Монстров и предметов ASCII-формат пока не хранит: у разобранной комнаты они пустые.

```
#######
#..@..#
#.....#
#######
```

## Недоверенные команды: `parseCommand`

`applyCommand` доверяет типам TypeScript, а в рантайме из сети придёт что угодно. Поэтому
на границе данные сначала проходят `parseCommand(raw: unknown): Command | null` — приём
«parse, don't validate»: `unknown` один раз превращается в строгий тип, дальше код работает
только с ним. Парсер собирает **новый** объект из известных полей (лишние поля и `__proto__`
отбрасываются), проверяет направление через `isDirection` и длину `playerId`.

Разделение ответственности:

- `parseCommand` проверяет только **форму** команды;
- `applyCommand` / `submitAction` — **правила** (есть ли такой игрок, ходит ли он ещё в этом ходу);
- сервер (шаг 6) — **кто прислал**: `playerId` подставляет из сессии, а не берёт из сообщения.

Без парсера одна команда с неизвестным направлением сохранялась в `pendingActions` и роняла
разрешение хода у всех — тест в `parseCommand.test.ts` это закрепляет.

## Очерёдность ходов: одновременные ходы

1. Игрок шлёт `{ type: 'submitAction', playerId, action }`, где `action` — `move` или `attack`
   с направлением, либо `wait`. Действие кладётся в `state.pendingActions`, клиенты получают
   `actionSubmitted`. Молча (без событий) игнорируются: повторный выбор в том же ходу,
   неизвестный id или id монстра, команды после конца игры (`status !== 'playing'`).
   Поиск по id — через `Object.hasOwn`, чтобы `'constructor'` и т.п. не находили ничего в прототипе.
2. Когда действие есть у **всех игроков**, `resolveTurn` применяет действия всех акторов
   одновременно, очищает `pendingActions` и увеличивает `turn`. События: `moved` / `bumped` /
   `waited` по каждому актору и в конце `turnResolved`.
3. Монстры ход не задерживают: их действие выбирается внутри `resolveTurn` перед
   `resolveMoves`. ИИ пока нет (шаг 4) — монстры стоят на месте и служат препятствием.
4. **`attack` пока ничего не делает** (бой — шаг 4): атакующий стоит на месте, как при `wait`,
   и получает событие `waited`. Клетку, в которую он целится, он не занимает.

**Конфликты** (`resolveMoves`) решаются без случайности и не зависят от порядка выбора:

| Ситуация                                          | Результат                   | `reason` в `bumped` |
| ------------------------------------------------- | --------------------------- | ------------------- |
| `wait` или `attack`                               | стоит, занимает свою клетку | —                   |
| Шаг в стену                                       | стоит                       | `wall`              |
| Двое в одну клетку                                | оба стоят                   | `contested`         |
| Двое меняются местами                             | оба стоят                   | `swap`              |
| В клетку того, кто стоит                          | стоит                       | `occupied`          |
| В клетку, которую сосед в этот же ход освобождает | проходит (цепочки работают) | —                   |

Алгоритм итеративный: провал одного может вызвать провал того, кто шёл за ним,
поэтому проверки повторяются, пока ничего не меняется.

Таймера хода нет: отошедший игрок блокирует всех. Если понадобится — он будет на сервере.

## client: сцены

`BootScene` → `MenuScene` ⇄ `GameScene` ⇄ `RoomEditorScene`. Ключи сцен и типы данных,
которые они передают друг другу, — в `scenes/sceneKeys.ts`.

| Сцена             | Заметки                                                                                                 |
| ----------------- | ------------------------------------------------------------------------------------------------------- |
| `BootScene`       | грузит тайлсет, спрайт-лист и покадровые анимации, регистрирует анимации                                |
| `MenuScene`       | фон — демо-карта; число игроков хранится в `game.registry` (переживает перезапуск сцен)                 |
| `GameScene`       | опрашивает клавиши в `update()`; пока идут анимации хода (`runningAnimations > 0`), ввод не принимается |
| `RoomEditorScene` | всё состояние — один `EditorDraft`; каждое изменение пересоздаёт карту целиком (комнаты маленькие)      |

Особенности, о которые уже спотыкались:

- **Две камеры.** Главная приближена (`ZOOM = 3`) и следует за героем, UI рисует отдельная
  камера в масштабе 1:1 (`ui/UiOverlay.ts`). Каждый новый объект нужно зарегистрировать:
  `ui.world(obj)` — только мир, `ui.add(obj)` — только UI. Иначе его нарисуют обе камеры.
- **Не использовать `Phaser.GameObjects.Layer` со спрайтами.** При остановке сцены слой
  уничтожается раньше вложенных спрайтов, и Phaser падает (`reading 'indexOf'`).
- **Пропуск хода — по нажатию, движение — по удержанию.** У шага есть анимация, которая
  тормозит повтор, у пропуска её нет, и удержание пролистывало бы ход каждый кадр.
- `main.ts` в dev-режиме кладёт игру в `window.__game` (для отладки и скила `run-game`).

## client: рендер карты

- `render/tilesetIndex.ts` — какие кадры тайлсета что означают (подробно — `docs/assets.md`).
- `render/autotile.ts` — **автотайлинг**: в `shared` клетка — просто `wall` или `floor`,
  а какой спрайт стены рисовать (верхняя грань, боковая, угол, перегородка), клиент решает
  по соседям. Пол прямо под стеной получает тайл с тенью. Стена без соседнего пола
  не рисуется — там фон `#25131a`. Вариант тайла выбирается хешем координат, а не
  случайно, чтобы картинка была стабильной.
- `render/mapView.ts` — `MapView`: тайлмап + декоративные факелы на верхних стенах.

## Хранение комнат

`storage/roomStorage.ts`, ключ localStorage `dt.rooms.v1`: массив `{ id, name, ascii }`.
При чтении битые записи пропускаются. Комнаты живут только в конкретном браузере,
для переноса — кнопка «ASCII» в редакторе.

## Тесты

Только `shared` (Vitest), файлы `*.test.ts` рядом с кодом. Состояние собирается явно,
обычно из ASCII-комнаты. Сейчас: карты, комнаты, начальное состояние (акторы, монстры, предметы),
ходы, все виды конфликтов движения, `attack`-заглушка, защита `submitAction` от чужих id,
`parseCommand` и генератор случайных чисел.

## Запуск в песочнице агента

Скил `.claude/skills/run-game` поднимает dev server и делает скриншоты через headless
Chromium (с кликами и нажатиями клавиш). Если папка смонтирована с Windows, pnpm не может
создать в ней симлинки, поэтому скил ставит зависимости в зеркало `/tmp/dt-run/ws`.
Подробности — в `SKILL.md`. На обычной машине достаточно `pnpm install && pnpm dev`.
